Préface

Pourquoi ce manuel

Claude Code n'est pas un chatbot. C'est un collaborateur agentique qui lit, écrit, exécute et se trompe — comme un junior brillant qu'il faut apprendre à cadrer.

L'arrivée de Claude Code a changé la texture du travail d'ingénieur. Là où un assistant classique attend votre question, Claude Code s'empare d'un dépôt, parcourt les fichiers, lance les tests, commite ses changements. Il travaille pendant que vous le regardez, ou pendant que vous êtes parti chercher un café — et parfois, pendant que vous dormez, grâce aux routines programmées sur le cloud.

Mais cette autonomie se mérite. Il faut apprendre à écrire un bon CLAUDE.md, à cadrer les permissions, à savoir quand ouvrir le mode plan, quand déléguer à un sous-agent, quand brancher un serveur MCP. Ce livre est le compagnon de cette courbe d'apprentissage.

À qui s'adresse ce livre

Aux développeurs qui ont installé Claude Code et qui se demandent comment en tirer réellement parti. Aux équipes qui veulent partager une base commune de conventions, de skills, de hooks. Aux responsables techniques qui doivent décider où placer le curseur entre autonomie et contrôle.

Aucun prérequis sinon : savoir ouvrir un terminal, être à l'aise avec git, et avoir déjà écrit quelques lignes de code.

Comment lire ce manuel

Les deux premiers chapitres posent les fondations : installation, boucle agentique, premier contact. Lisez-les dans l'ordre. Les suivants sont des modules indépendants — CLAUDE.md, skills, hooks, MCP, subagents — que vous pouvez parcourir à la carte selon vos besoins. L'annexe sert de référence quand vous ne vous souvenez plus du flag --add-dir ou du format d'un hook.

Convention

Les commandes à taper dans un terminal sont préfixées par $ dans ce livre, mais vous ne tapez jamais ce caractère. Les commandes à taper dans Claude Code lui-même (après avoir lancé claude) sont présentées sans préfixe.

Un mot sur les versions

Claude Code évolue vite. Les fonctionnalités décrites ici reflètent l'état du produit à l'édition 2026 de ce manuel. Les captures de flags obscurs vieillissent plus vite que les principes. Quand une commande ne fait pas ce que ce livre annonce, votre premier réflexe doit être claude --version, puis la documentation officielle à code.claude.com.

Chapitre 01

Prise en main

Installer Claude Code, lancer sa première session, et comprendre la boucle « explorer, planifier, implémenter, commiter » qui structure 90 % de l'usage quotidien.

Installer Claude Code

Claude Code est disponible comme CLI sur macOS, Linux et Windows, comme extension VS Code et JetBrains, comme application Desktop, et dans le navigateur à claude.ai/code. Tous ces canaux partagent le même moteur et les mêmes fichiers de configuration : votre CLAUDE.md, vos skills et vos serveurs MCP fonctionnent partout.

Installation native (recommandée)

Sur macOS, Linux ou WSL :

$ curl -fsSL https://claude.ai/install.sh | bash

Sur Windows PowerShell :

PS> irm https://claude.ai/install.ps1 | iex

Les installations natives se mettent à jour en arrière-plan. Vous restez sur la dernière version sans y penser.

Autres canaux

# macOS, via Homebrew
$ brew install --cask claude-code

# Windows, via WinGet
$ winget install Anthropic.ClaudeCode

Les installations Homebrew et WinGet ne se mettent pas à jour automatiquement. Prévoyez un brew upgrade claude-code de temps en temps.

Attention

Sur Windows natif, installez Git for Windows avant Claude Code. Sans lui, l'outil Bash est remplacé par PowerShell et de nombreux scripts cessent de fonctionner. En WSL, aucun besoin.

Première session

Rendez-vous dans un projet existant et lancez : 

$ cd mon-projet
$ claude

Au premier lancement, Claude Code ouvre un navigateur pour l'authentification. Trois formules sont acceptées :

  • Abonnement Claude Pro, Max, Team ou Enterprise — recommandé.
  • Compte Claude Console (crédits API prépayés), qui crée automatiquement un workspace « Claude Code » pour suivre les coûts.
  • Fournisseur cloud tiers : Amazon Bedrock, Google Vertex AI, Microsoft Foundry.

Les identifiants sont stockés localement. Vous ne vous reconnecterez plus, sauf si vous tapez /login pour changer de compte.

Vos premières commandes

Une fois connecté, l'écran de bienvenue affiche votre historique. Essayez d'abord des questions sur votre projet, sans rien lui demander de modifier : 

que fait ce projet ?
quelles technologies sont utilisées ?
où est le point d'entrée principal ?
explique la structure des dossiers

Claude parcourt vos fichiers à la demande. Vous n'avez pas besoin de pointer vers des chemins précis ni de copier-coller du code dans le prompt.

Un premier changement

Après l'exploration, demandez un changement concret : 

ajoute une fonction hello world dans le fichier principal

Claude Code va localiser le fichier adéquat, vous montrer le diff proposé, puis demander confirmation. Approuvez le changement, et l'édition est appliquée. Rien n'est écrit sur votre disque sans votre accord explicite (sauf si vous avez activé un mode plus permissif — voir chapitre 9).

Astuce

Appuyez sur Shift+Tab pour cycler les modes de permission dans la session courante : par défaut, accept-edits, plan, auto, ou bypass. L'indicateur en bas d'écran change de couleur.

Les quatre temps du travail agentique

Un développeur chevronné avec Claude Code ne lui balance pas une demande dense d'un bloc. Il structure la session en quatre temps :

  1. Explorer — en mode plan, Claude lit les fichiers et répond sans rien modifier.
  2. Planifier — demandez un plan d'implémentation détaillé, modifiez-le au besoin (Ctrl+G l'ouvre dans votre éditeur).
  3. Implémenter — quittez le mode plan et laissez Claude coder en vérifiant par rapport au plan.
  4. Commiter — « commit avec un message descriptif et ouvre une PR ».

Ce rythme n'est pas obligatoire — pour corriger un typo, allez droit au but. Mais pour toute tâche touchant plusieurs fichiers, il économise énormément de corrections rétroactives.

Lexique express

TermeSignification
claudeLance une session interactive dans le répertoire courant.
claude -p "…"Mode non-interactif : une requête, puis la main vous est rendue.
claude -cReprend la dernière conversation du dossier.
claude -rReprend une conversation précédente parmi une liste.

Chapitre 02

Comment Claude Code pense

Un modèle de langage, une boucle agentique, une fenêtre de contexte qui se remplit. Comprendre ces trois mécaniques transforme votre manière de prompter.

La boucle agentique

Sous le capot, Claude Code tourne en boucle : il reçoit un message, décide d'un ou plusieurs appels d'outils (lire un fichier, lancer une commande, chercher dans le code), observe les résultats, puis décide à nouveau. Cette boucle s'arrête quand il estime la tâche terminée ou quand il vous rend la parole.

Les outils fondamentaux sont peu nombreux :

  • Read et Write pour les fichiers.
  • Edit pour les modifications précises par chaîne.
  • Glob et Grep pour la recherche.
  • Bash pour toute commande système.
  • WebFetch, WebSearch pour l'extérieur.
  • Agent pour déléguer à un subagent spécialisé.

S'y ajoutent les outils fournis par vos serveurs MCP et vos skills. Chaque appel coûte des tokens et du temps : la qualité de Claude dépend de la qualité de ces décisions successives.

La fenêtre de contexte

Tout ce que Claude Code voit — système, CLAUDE.md, votre message, les fichiers lus, les sorties de commandes, les résultats de recherche — vit dans une seule fenêtre de contexte. Cette fenêtre a une taille limite (200 000, 1 million de tokens selon le modèle), et la performance se dégrade bien avant qu'elle ne soit pleine.

C'est la contrainte fondamentale. Toutes les bonnes pratiques — /clear entre deux tâches, délégation à des subagents, tool search MCP, path-scoped rules — se résument à : garder le contexte propre.

À retenir

Si vous corrigez Claude deux fois sur le même point dans une session, le contexte est déjà pollué par les tentatives ratées. Un /clear suivi d'un prompt plus précis bat systématiquement l'accumulation de corrections.

Qu'est-ce qui survit à la compaction ?

Quand la fenêtre approche sa limite, Claude Code compacte automatiquement l'historique : il résume les anciens tours en préservant le code et les décisions importantes. Ce qui survit toujours :

  • Votre CLAUDE.md racine, rechargé depuis le disque.
  • Les skills les plus récemment invoqués (jusqu'à 25 000 tokens combinés).
  • Le résumé de ce qui précède.

Ce qui ne survit pas de manière garantie : les CLAUDE.md imbriqués dans des sous-dossiers (ils se rechargeront à la prochaine lecture d'un fichier de ce dossier), les skills anciens, les instructions données uniquement par chat.

Modes de permission

Chaque session tourne dans un mode qui définit ce que Claude peut faire sans vous demander :

ModeComportementQuand l'utiliser
defaultDemande pour toute action modifiante.Première session dans un dépôt inconnu.
planLecture seule, propose un plan.Phase d'exploration et de planification.
acceptEditsApprouve automatiquement les édits de fichiers.Vous suivez le travail en direct.
autoUn classificateur juge chaque commande.Tâches longues où vous faites confiance au cadrage.
bypassPermissionsRien n'est demandé.CI/CD, sandbox jetable, ou vous savez ce que vous faites.

Modèles et effort

Claude Code peut utiliser plusieurs modèles de la famille Claude 5 — Opus 5.5 pour les raisonnements difficiles, Sonnet 5.5 pour l'équilibre coût/qualité, Haiku 5.5 pour la vitesse. Changez à la volée avec /model. L'effort de raisonnement se règle avec /effort (low, medium, high, xhigh, max) et peut être modulé par skill.

Pour un one-shot particulièrement coriace, insérez le mot ultrathink dans votre prompt : il déclenche un raisonnement approfondi sur ce tour uniquement.

Chapitre 03

CLAUDE.md et la mémoire

Le fichier que Claude lit au début de chaque session, et la mémoire automatique qu'il tient tout seul. Deux systèmes complémentaires pour que votre assistant retienne votre projet.

Deux mémoires, deux auteurs

Chaque session démarre avec un contexte frais. Pour que Claude ne redécouvre pas votre projet à chaque fois, il existe deux systèmes de mémoire persistante, chargés tous les deux au démarrage.

CLAUDE.mdMémoire automatique
Écrit parVousClaude
ContientInstructions, règlesApprentissages, commandes découvertes
PortéeProjet, utilisateur, organisationPar dépôt, partagée entre worktrees
Idéal pourStandards de code, architecturePréférences découvertes, commandes de build

Où placer un CLAUDE.md

Plusieurs emplacements sont possibles. Les instructions se cumulent des plus génériques aux plus spécifiques :

PortéeEmplacementPartagé avec
Politique managée/Library/Application Support/ClaudeCode/CLAUDE.md (macOS), /etc/claude-code/CLAUDE.md (Linux)Toute l'organisation
Utilisateur~/.claude/CLAUDE.mdVous, sur tous vos projets
Projet./CLAUDE.md ou ./.claude/CLAUDE.mdL'équipe, via git
Local projet./CLAUDE.local.mdVous seul (à ajouter au .gitignore)

Générer un premier CLAUDE.md

Dans votre projet, tapez simplement : 

/init

Claude parcourt le code, détecte le build system, les frameworks de test, les conventions, et génère un CLAUDE.md de départ. S'il existe déjà, il propose des améliorations plutôt que de l'écraser. Partez de là, taillez, affinez.

Écrire des instructions efficaces

Un bon CLAUDE.md tient en moins de 200 lignes. Au-delà, il consomme trop de contexte et perd en adhérence : Claude peut « oublier » les règles noyées dans le bruit. Testez chaque ligne avec cette question : « Si je retire ceci, Claude fera-t-il des erreurs ? » Si non, supprimez.

À inclureÀ exclure
Commandes bash non devinables (make deploy-staging)Ce que Claude découvrira en lisant le code
Règles de style qui diffèrent des défautsConventions standard du langage
Instructions de test, test runner préféréDocumentation API détaillée (mettez un lien)
Étiquette dépôt (branches, PR)Informations qui changent souvent
Décisions architecturales spécifiquesDescriptions fichier-par-fichier
Variables d'env requises, gotchasLes évidences (« écrire du code propre »)

Exemple minimal

# Style
- Modules ES (import/export), pas de CommonJS
- Déstructurer les imports quand possible

# Workflow
- Lancer `pnpm typecheck` après une série de modifications
- Préférer `pnpm test <file>` à la suite complète pour aller plus vite

# Gotchas
- Les migrations tournent avec DATABASE_URL exportée
- `./scripts/dev.sh` démarre Postgres + Redis + le serveur

Rules path-scopées

Pour un gros projet, découpez les règles en fichiers thématiques sous .claude/rules/. Chaque fichier peut déclarer un champ paths en frontmatter : il ne sera chargé que lorsque Claude lira un fichier qui matche. 

---
paths:
  - "src/api/**/*.ts"
---

# Règles API
- Toute route doit valider ses entrées (zod)
- Format d'erreur standard : { code, message, details }
- Documenter avec un commentaire OpenAPI

La mémoire automatique

Depuis Claude Code 2.1.59, l'outil tient tout seul un petit journal à ~/.claude/projects/<projet>/memory/. Il y écrit des apprentissages : commandes de build qui ont marché, bugs récurrents, préférences découvertes au fil des corrections. Rien n'est écrit sans discernement — Claude juge ce qui mérite d'être retenu.

Le fichier d'index MEMORY.md est chargé au démarrage (ses 200 premières lignes ou 25 Ko). Les fichiers thématiques — debugging.md, api-conventions.md — sont lus à la demande.

Pour auditer ce que Claude a mémorisé, tapez /memory dans une session : vous voyez les CLAUDE.md chargés et un lien vers le dossier de mémoire automatique.

Astuce

Dites simplement à Claude : « retiens que ce projet utilise pnpm, pas npm ». Il sauvegardera dans sa mémoire automatique. Pour ajouter dans CLAUDE.md plutôt : « ajoute cette règle à CLAUDE.md ».

Importations et héritage

Un CLAUDE.md peut inclure d'autres fichiers avec la syntaxe @chemin : 

Voir @README.md pour la vue d'ensemble et @package.json pour les commandes npm.

# Instructions supplémentaires
- Workflow git : @docs/git-instructions.md
- Préférences perso : @~/.claude/mes-prefs.md

Les chemins relatifs sont résolus par rapport au fichier qui importe. Profondeur maximale : 5 niveaux. Si un dépôt expose déjà un AGENTS.md, créez simplement un CLAUDE.md qui l'importe — les deux outils liront la même source.

Chapitre 04

Skills — compétences réutilisables

Quand une procédure revient trop souvent dans vos prompts, elle mérite son propre fichier. Les skills sont la brique d'extension la plus simple et la plus partageable de Claude Code.

Qu'est-ce qu'un skill ?

Un skill est un dossier contenant un fichier SKILL.md. Ce fichier a un frontmatter YAML qui dit quand l'utiliser, et un corps en markdown qui dit quoi faire. Claude peut le charger automatiquement quand votre prompt matche, ou vous l'invoquez manuellement avec /nom-du-skill.

La différence fondamentale avec un CLAUDE.md : le corps d'un skill ne se charge que lorsqu'il est invoqué. Votre long guide de deploiement peut faire 500 lignes sans peser sur le contexte au démarrage. Seule la description vit en permanence pour que Claude sache qu'elle existe.

Créer son premier skill

Créons un skill qui résume les changements non commitées et signale ce qui est risqué. 

$ mkdir -p ~/.claude/skills/resumer-changements

Puis dans ~/.claude/skills/resumer-changements/SKILL.md : 

---
description: Résume les changements non commités et flag ce qui est risqué.
  À utiliser quand l'utilisateur demande ce qui a changé, un message de
  commit, ou veut une revue de son diff.
---

## Changements actuels

!`git diff HEAD`

## Instructions

Résume les changements ci-dessus en deux ou trois puces, puis liste les
risques : erreurs non traitées, valeurs en dur, tests à mettre à jour.
Si le diff est vide, dis-le simplement.

La ligne !`git diff HEAD` est une injection de contexte dynamique : la commande est exécutée avant que Claude voie le contenu du skill. Le résultat est inséré à sa place. Claude reçoit donc un prompt déjà rempli avec le diff réel.

Emplacements

EmplacementPortée
~/.claude/skills/<nom>/SKILL.mdTous vos projets
.claude/skills/<nom>/SKILL.mdCe projet uniquement (partagé via git)
Dans un pluginPartout où le plugin est actif
ManagedToute l'organisation

Frontmatter : les champs qui comptent

---
description: Déploie l'application en production
disable-model-invocation: true
allowed-tools: Bash(git *) Bash(pnpm *)
argument-hint: [environnement]
model: opus
effort: high
---
  • description — ce qui aide Claude à décider d'activer le skill. Mettez les mots-clés que vous diriez naturellement.
  • disable-model-invocation — true pour les actions à effets de bord : /deploy, /send-slack. Claude ne les lance jamais tout seul.
  • allowed-tools — outils pré-autorisés tant que le skill est actif, sans demande à l'utilisateur.
  • argument-hint — s'affiche dans l'autocomplétion.
  • paths — glob patterns qui limitent le déclenchement automatique à certains fichiers.
  • context: fork — exécute le skill dans un subagent isolé, avec son propre contexte.

Arguments

Un skill peut recevoir des arguments. Dans le corps : 

---
name: fix-issue
description: Corrige un ticket GitHub
---

Corrige le ticket GitHub $ARGUMENTS en suivant nos conventions.

1. Lis la description via `gh issue view`
2. Comprends le problème
3. Implémente le correctif
4. Écris les tests
5. Crée un commit avec un message descriptif

Vous invoquez /fix-issue 123 et $ARGUMENTS devient 123. Pour accéder aux arguments par position : $0, $1, etc.

Skills avec fichiers de support

Un skill peut embarquer des scripts, des templates, des exemples : 

mon-skill/
├── SKILL.md           # Point d'entrée (requis)
├── reference.md       # Documentation détaillée (lue au besoin)
├── examples.md        # Exemples d'usage
└── scripts/
    └── helper.py      # Script Python exécutable

Référencez ces fichiers depuis SKILL.md pour que Claude sache quoi lire quand. Utilisez ${CLAUDE_SKILL_DIR} dans les commandes pour pointer vers le bon dossier : 

Génère la visualisation en lançant :
```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/visualize.py .
```

Chapitre 05

Hooks — automatiser le cycle de vie

Là où CLAUDE.md et les skills sont des conseils, les hooks sont des garanties : des scripts qui s'exécutent à des moments précis, quoi que Claude décide par ailleurs.

Quand utiliser un hook

Si une action doit se produire à chaque fois, sans exception, c'est un hook. Formater après chaque édition, lancer le linter avant un commit, bloquer les écritures dans un dossier sensible — ces règles ne doivent pas dépendre du jugement du modèle.

Anatomie d'un hook

Les hooks sont déclarés dans un fichier settings.json. La structure a trois niveaux : l'événement, un matcher optionnel, la liste des hooks à exécuter. 

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "prettier",
            "args": ["--write", "${tool_input.file_path}"]
          }
        ]
      }
    ]
  }
}

Où placer settings.json

EmplacementPortéePartageable
~/.claude/settings.jsonVos sessions, tous projetsNon
.claude/settings.jsonProjetOui, via git
.claude/settings.local.jsonProjet, localNon (.gitignore)
Managed policyToute l'organisationVia MDM / Group Policy

Les événements qui comptent

CadenceÉvénements
Une fois par sessionSessionStart, SessionEnd
Une fois par tourUserPromptSubmit, Stop, StopFailure
À chaque appel d'outilPreToolUse, PostToolUse, PostToolUseFailure
AsynchronesFileChanged, ConfigChange, CwdChanged, Notification

SessionStart : injecter du contexte

Un hook SessionStart peut charger du contexte dynamique (tickets ouverts, status git, résultats CI récents) et le pousser dans la session : 

{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/load-context.sh"
          }
        ]
      }
    ]
  }
}

Le script écrit sur stdout un JSON avec un champ additionalContext, ou simplement du texte qui sera injecté avant le premier tour. Gardez-le rapide : il tourne à chaque session.

PreToolUse : bloquer les commandes dangereuses

#!/bin/bash
command=$(jq -r '.tool_input.command')

if echo "$command" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Commande destructive bloquée"
    }
  }'
else
  exit 0
fi

PostToolUse : linter, formater, valider

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "eslint", "args": ["${tool_input.file_path}", "--fix"] }
        ]
      }
    ]
  }
}

Types de hooks

  • command — un script shell, reçoit du JSON sur stdin.
  • http — un POST JSON vers un endpoint HTTP.
  • mcp_tool — appelle un outil d'un serveur MCP connecté.
  • prompt — envoie un texte à Claude pour une décision oui/non.
  • agent — lance un subagent pour une validation complexe (expérimental).

Communiquer avec Claude

Un hook communique via son code de sortie et son JSON de sortie :

  • Exit 0 : succès ; stdout parsé comme JSON optionnel.
  • Exit 2 : erreur bloquante ; stderr affiché à l'utilisateur.
  • Autre code : erreur non bloquante, l'exécution continue.

Le JSON de sortie peut porter plusieurs champs : 

{
  "continue": true,
  "systemMessage": "Avertissement affiché à Claude",
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Explication",
    "additionalContext": "Info utile pour Claude"
  }
}

Hooks dans les skills et les subagents

Un skill peut déclarer ses propres hooks en frontmatter, qui ne vivent que lorsqu'il est actif : 

---
name: migration-db
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/validate-sql.sh"
---

Visualiser les hooks actifs

Dans une session, tapez /hooks. Vous voyez tous les hooks configurés avec leur événement, matcher, source et commande. Pratique pour déboguer un comportement surprenant.

Sécurité

Les hooks de niveau projet ne s'activent qu'après que vous ayez accepté la boîte de dialogue de confiance pour le dépôt. Avant de cloner un dépôt tiers, examinez son .claude/ — un hook malveillant peut exécuter n'importe quoi sur votre machine.

Chapitre 06

MCP — connecter Claude à vos outils

Le Model Context Protocol permet à Claude d'interroger votre JIRA, de requêter votre base PostgreSQL, de lire vos Figma, de créer des drafts Gmail. Un standard ouvert, des centaines de serveurs.

Pourquoi MCP

Quand vous collez le contenu d'un ticket JIRA dans votre prompt, puis le texte d'un dashboard Sentry, puis une requête SQL — vous faites manuellement le travail qu'un serveur MCP ferait pour vous. Branchez-le une fois, et Claude lit et agit directement sur ces systèmes.

Ajouter un serveur MCP

Trois transports existent. Le plus courant est HTTP, utilisé par les services cloud : 

# HTTP (recommandé pour les services cloud)
$ claude mcp add --transport http notion https://mcp.notion.com/mcp

# Avec un Bearer token
$ claude mcp add --transport http github https://api.githubcopilot.com/mcp/ \
    --header "Authorization: Bearer YOUR_PAT"

# Local, stdio (outil en ligne de commande sur votre machine)
$ claude mcp add --transport stdio --env AIRTABLE_API_KEY=xxx airtable \
    -- npx -y airtable-mcp-server
Important

L'ordre compte. Toutes les options (--transport, --env, --scope, --header) viennent avant le nom du serveur. Le double tiret -- sépare le nom du serveur de la commande qui lui est passée.

Portées de configuration

PortéeCharge dansPartagéeStockée dans
local (défaut)Ce projet uniquementNon~/.claude.json

Précisez la portée avec --scope project pour qu'un serveur soit versionné dans .mcp.json à la racine du projet et bénéficie à toute l'équipe.

Gérer les serveurs

$ claude mcp list              # lister
$ claude mcp get github        # détails
$ claude mcp remove github     # supprimer

# Dans une session Claude
/mcp                           # statut, OAuth, auth

Authentification OAuth

Beaucoup de serveurs cloud utilisent OAuth 2.0. La procédure : vous ajoutez le serveur, Claude le marque comme nécessitant une authentification au premier appel (via un 401), vous tapez /mcp pour lancer le flow dans votre navigateur. Les tokens sont stockés dans votre keychain et rafraîchis automatiquement.

Variables d'environnement dans .mcp.json

Les configurations partagées en équipe doivent rester flexibles. Utilisez l'expansion de variables : 

{
  "mcpServers": {
    "api": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      }
    }
  }
}

La syntaxe ${VAR:-defaut} fournit une valeur de repli. Idéal pour partager un .mcp.json sans y mettre de secrets.

Tool Search : la clé du passage à l'échelle

Charger les schémas de 50 outils MCP au démarrage inonderait votre fenêtre de contexte. Tool Search diffère ce chargement : seuls les noms des outils sont présents, et Claude cherche ceux dont il a besoin à la demande.

Activé par défaut (sauf sur Vertex AI et proxies non-first-party). Pour forcer un comportement : 

$ ENABLE_TOOL_SEARCH=auto:5 claude   # seuil à 5% du contexte
$ ENABLE_TOOL_SEARCH=false claude    # tout charger upfront

Un serveur dont les outils doivent toujours être visibles peut déclarer alwaysLoad: true dans son entrée .mcp.json.

Référencer des ressources MCP

Comme pour les fichiers avec @, vous pouvez référencer une ressource exposée par un serveur : 

Analyse @github:issue://123 et propose un fix
Compare @postgres:schema://users avec @docs:file://database/user-model

Prompts MCP comme commandes

Les serveurs peuvent exposer des prompts, qui apparaissent comme des commandes slash : 

/mcp__github__list_prs
/mcp__jira__create_issue "Bug dans le login" high
Astuce

Si vous utilisez Claude Desktop en parallèle, claude mcp add-from-claude-desktop importe vos serveurs déjà configurés là-bas.

Chapitre 07

Subagents et parallélisation

Quand une tâche menace d'inonder votre contexte, déléguez-la à un subagent. Il travaille dans sa propre fenêtre et vous rend un résumé propre.

À quoi servent les subagents

Imaginez : vous demandez à Claude « cherche comment on gère le refresh de token dans ce projet ». Il va lire une vingtaine de fichiers. Tous ces fichiers vont consommer votre contexte, alors que vous ne voulez qu'une synthèse. Un subagent fait exactement cela : il explore dans son coin, et vous rend trois paragraphes.

Les quatre bénéfices concrets :

  • Préservation du contexte : la recherche reste hors de votre conversation.
  • Contraintes outillées : chaque subagent a son propre jeu d'outils autorisés.
  • Réutilisation : les subagents utilisateurs sont partagés entre projets.
  • Contrôle des coûts : router les tâches rapides vers Haiku, les ardues vers Opus.

Les subagents intégrés

NomRôleOutils
ExploreRecherche de code rapide, lecture seuleGlob, Grep, Read, WebFetch
PlanArchitecture, plans d'implémentationLecture, recherche, pas d'édition
general-purposeFourre-tout pour recherches et tâches multi-étapesTous les outils
statusline-setupConfigure la ligne de statutRead, Edit

Créer un subagent personnalisé

Un subagent est un fichier markdown avec frontmatter, dans .claude/agents/ (projet) ou ~/.claude/agents/ (utilisateur) : 

---
name: security-reviewer
description: Revoit le code pour trouver des vulnérabilités de sécurité
tools: Read, Grep, Glob, Bash
model: opus
---

Tu es un ingénieur sécurité senior. Revois le code pour :
- Injections (SQL, XSS, command injection)
- Failles d'authentification et d'autorisation
- Secrets ou credentials en dur
- Gestion non sécurisée des données

Fournis les références précises de ligne et des correctifs suggérés.

Puis invoquez-le explicitement : « utilise un subagent pour revoir ce code côté sécurité ».

Déléguer en parallèle

Depuis un prompt, vous pouvez demander plusieurs subagents en même temps. Claude le fera en parallèle quand les tâches sont indépendantes : 

Lance en parallèle trois audits :
1. un subagent qui vérifie les tests manquants
2. un subagent qui cherche les TODO et FIXME
3. un subagent qui scanne les dépendances obsolètes

Précharger des skills dans un subagent

Le frontmatter skills injecte des skills directement dans le contexte initial du subagent : 

---
name: pr-reviewer
description: Revoit les pull requests selon nos conventions
tools: Read, Grep, Bash(gh *)
skills:
  - api-conventions
  - testing-standards
---

Mémoire persistante par subagent

Chaque subagent peut avoir sa propre mémoire automatique. Pour l'activer, ajoutez enable-persistent-memory: true en frontmatter. Le subagent accumule alors ses propres apprentissages sans polluer la mémoire principale du projet.

Agents en arrière-plan et équipes

Au-delà des subagents dans une session, Claude Code supporte des modes de collaboration à plus grande échelle :

  • Background agents — plusieurs sessions complètes tournent en parallèle, pilotées depuis une vue unique.
  • Agent teams — un chef d'équipe orchestre plusieurs agents avec messagerie et tâches partagées.
  • Agent SDK — pour construire vos propres agents avec contrôle total sur l'orchestration, les outils et les permissions.
Pattern utile

Writer / Reviewer. Une session écrit la fonctionnalité. Une seconde, démarrée fraîche, revoit le code sans biais pour le code qu'elle vient d'écrire. Puis la première reprend les retours. Résultat : qualité en nette hausse pour un coût marginal.

Référencer avec @

Tapez @ dans un prompt pour voir l'autocomplétion. Vous pouvez référencer :

  • Des fichiers : @src/auth/login.ts — Claude le lit avant de répondre.
  • Des ressources MCP : @github:issue://123, @docs:file://api/auth.
  • Des répertoires : @src/components/ — Claude explore le dossier.

Entrée riche

  • Images — copiez-collez ou glissez-déposez. Idéal pour mocks, erreurs de UI, screenshots.
  • URL — mettez l'URL, Claude la fetche. Allowlistez les domaines fréquents dans /permissions.
  • Pipes — cat error.log | claude -p "explique".

Status line personnalisée

La ligne de statut en bas d'écran peut être personnalisée pour afficher ce qui compte pour vous : branche git, usage du contexte, modèle actif, coût courant. Lancez statusline-setup (le subagent dédié) pour la configurer en interactif.

Modes d'édition

Au-delà du mode conversation standard, deux modes modifient la boucle :

  • Plan mode — Claude lit, analyse, propose un plan, mais ne modifie rien. Entrez-y avec Shift+Tab ou en invoquant un subagent de type Plan.
  • Accept-edits mode — les édits de fichiers passent sans demander. Pratique pendant une session guidée où vous suivez les diffs.
Astuce

Pour les tâches où le scope est clair et le fix minuscule (corriger une faute, renommer une variable), sautez la phase plan — elle ajoute de l'overhead inutile. Le plan excelle quand la tâche touche plusieurs fichiers ou que l'approche est incertaine.

Chapitre 09

Permissions et sécurité

Entre « tout demander » et « ne rien demander », il y a quatre modes, des règles fines par outil, et un sandbox pour isoler l'OS. Trouvez votre équilibre.

Les quatre modes

Chaque session tourne dans un mode qui décide ce qui est autorisé automatiquement. Vous le changez à la volée avec Shift+Tab ou vous le fixez au lancement avec --permission-mode.

  • default — Claude demande pour toute action modifiante.
  • acceptEdits — édits de fichiers automatiques, bash encore demandé.
  • auto — un classificateur juge chaque action : les routines passent, les actions risquées sont bloquées ou escaladées.
  • bypassPermissions — rien n'est demandé. Pour CI, sandbox jetable, ou si vous avez pleine confiance dans le cadrage.

Règles fines : /permissions

La commande /permissions ouvre un éditeur où vous définissez des règles par outil. Vous pouvez allowlister certaines commandes bash spécifiques tout en demandant confirmation pour le reste : 

{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Edit(src/**/*.ts)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Edit(.env*)",
      "Write(.env*)"
    ],
    "ask": [
      "Bash(git push *)"
    ]
  }
}

Les trois listes se combinent : deny est absolu, allow passe sans demander, ask demande explicitement même en mode auto, et le reste suit le mode courant.

Sandbox

Le mode sandbox isole la session au niveau de l'OS : les écritures fichier sont limitées à certains chemins, l'accès réseau est restreint. Lancez /sandbox ou activez-le dans vos settings : 

{
  "sandbox": {
    "enabled": true,
    "writablePaths": ["${CLAUDE_PROJECT_DIR}", "/tmp"],
    "networkAccess": "allowlist",
    "allowedHosts": ["github.com", "registry.npmjs.org"]
  }
}

C'est le compagnon idéal du mode bypassPermissions : vous laissez Claude travailler sans questions, mais tout ce qu'il peut faire reste dans un périmètre défini.

Secrets : ne jamais commiter par mégarde

Trois mesures combinées protègent vos secrets :

  • Un deny explicite sur .env* dans les permissions.
  • Un hook PreToolUse qui scanne les diffs avant commit.
  • Un CLAUDE.md qui rappelle « ne jamais mettre de credentials dans le code ».

Les trois sont nécessaires parce qu'ils ont des temporalités différentes : CLAUDE.md guide l'intention, le hook bloque l'action, le deny protège les fichiers sensibles.

Protection contre les prompt injections

Un serveur MCP qui lit du contenu externe (JIRA, GitHub, email) peut recevoir du texte malveillant qui tente de rediriger Claude. Deux garde-fous :

  • Claude Code traite tout texte provenant d'une source externe comme données, jamais comme instruction.
  • Les actions à effet de bord (push, delete, send) demandent toujours confirmation, même en auto, pour les sources externes.

Pour les workflows automatisés sur du contenu externe (triage d'issues, autofix de PR), gardez un humain dans la boucle sur les actions irréversibles.

Settings managés en entreprise

Pour une organisation qui déploie Claude Code à grande échelle, un fichier de settings managés peut être poussé via MDM ou Group Policy à un emplacement spécifique :

  • macOS : /Library/Application Support/ClaudeCode/managed-settings.json
  • Linux : /etc/claude-code/managed-settings.json
  • Windows : C:\Program Files\ClaudeCode\managed-settings.json

Les règles managées ne peuvent pas être affaiblies par les settings utilisateur ou projet. Elles permettent de verrouiller la méthode d'authentification (forceLoginMethod), de bloquer certains outils ou chemins, ou d'imposer un sandbox.

Chapitre 10

Travailler partout

Terminal, VS Code, JetBrains, Desktop, Web, iOS. Vos sessions ne sont pas liées à une surface — elles se déplacent avec vous.

Le même moteur, plusieurs surfaces

Toutes les interfaces de Claude Code partagent le même moteur. Vos CLAUDE.md, vos skills, vos serveurs MCP, votre historique — tout est accessible où que vous travailliez. Choisissez la surface selon le contexte, pas selon les fonctionnalités.

Terminal

Le canal canonique. L'intégralité des fonctions, la latence la plus basse, l'intégration shell la plus naturelle. claude dans n'importe quel dossier.

VS Code et Cursor

L'extension VS Code apporte des diffs inline, les mentions @, la revue de plan, l'historique de conversation directement dans l'éditeur. Installation : rechercher « Claude Code » dans la vue Extensions (Cmd+Shift+X).

Ouvrez-la ensuite via la Command Palette : Cmd+Shift+P → Claude Code: Open in New Tab.

JetBrains

Un plugin pour IntelliJ IDEA, PyCharm, WebStorm et toute la suite JetBrains. Vue de diff interactive, partage de contexte de la sélection. Installez-le depuis le JetBrains Marketplace, puis redémarrez l'IDE.

Desktop

Une application native pour macOS et Windows. Idéale pour :

  • Revoir visuellement les diffs avant d'accepter.
  • Faire tourner plusieurs sessions côte à côte dans leurs worktrees.
  • Planifier des routines qui tournent sur votre machine, avec accès complet aux outils locaux.
  • Lancer des sessions cloud et revenir voir leur résultat.

Depuis une session terminal, tapez /desktop pour transférer la session dans l'app desktop et profiter de l'interface visuelle sans perdre votre contexte.

Web

claude.ai/code permet de lancer des sessions directement dans le navigateur, sur une infra gérée par Anthropic. Aucun setup local. Idéal pour :

  • Lancer des tâches longues et revenir voir le résultat.
  • Travailler sur des dépôts que vous n'avez pas en local.
  • Faire tourner plusieurs tâches en parallèle sans encombrer votre machine.

La session cloud a sa propre VM, les repos sont clonés frais à chaque démarrage. Pensez à commiter et pousser pour conserver votre travail.

Mobile et Remote Control

L'app Claude iOS permet de lancer des tâches depuis votre téléphone. Avec Remote Control, vous pouvez même piloter une session locale (sur votre Mac) depuis votre téléphone, utile pour relire une PR en déplacement ou envoyer une instruction pendant qu'une tâche longue tourne chez vous.

Teleport : passer d'une surface à l'autre

Lancez une tâche sur le web, puis récupérez-la dans votre terminal local : 

$ claude --teleport

Claude vous propose vos sessions cloud actives à importer dans la session locale. Vous reprenez pile où vous en étiez.

Intégrations chat et CI

  • Slack — mentionnez @Claude avec un bug ou une demande, et il revient avec une PR.
  • GitHub Actions et GitLab CI/CD — automatisation des revues et du triage des issues.
  • Chrome — l'extension permet à Claude de tester vos UI dans le navigateur.
  • Channels — Telegram, Discord, iMessage, webhooks arbitraires peuvent pousser des événements dans une session.

Dispatch — l'orchestrateur mobile

Depuis l'app Desktop, Dispatch sert d'inbox pour vos demandes mobiles. Envoyez une tâche depuis votre téléphone, Dispatch spawn une session Desktop pour l'exécuter, vous recevez une notification quand c'est prêt. Utile pour transformer un trajet de métro en productivité.

Chapitre 11

Automatisation et CI/CD

Mode non-interactif, routines programmées, pipelines, Agent SDK. Comment multiplier votre impact une fois les fondamentaux maîtrisés.

Le mode non-interactif

Le drapeau -p transforme Claude Code en commande Unix composable. Une requête, une réponse, puis la main. Idéal pour les scripts, les hooks pre-commit, les pipelines CI. 

# Question ponctuelle
$ claude -p "Explique ce que fait ce projet"

# Sortie structurée pour les scripts
$ claude -p "Liste toutes les routes API" --output-format json

# Streaming pour traitement temps réel
$ claude -p "Analyse ce log" --output-format stream-json

Pipeline Unix

Composez avec le reste de l'écosystème Unix : 

# Analyser les anomalies dans un log
$ tail -200 app.log | claude -p "Signale les anomalies"

# Traduire les strings et ouvrir une PR
$ claude -p "Traduis les nouvelles strings en français et crée une PR"

# Revue sécurité sur les fichiers modifiés
$ git diff main --name-only | claude -p "Analyse ces fichiers côté sécurité"

Fan-out sur des listes de fichiers

Pour une grosse migration, générez la liste des fichiers, puis bouclez : 

$ for file in $(cat files.txt); do
    claude -p "Migre $file de React à Vue. Réponds OK ou FAIL." \
      --allowedTools "Edit,Bash(git commit *)"
  done

Testez d'abord sur 2-3 fichiers, affinez le prompt, puis lancez sur l'ensemble. Le flag --allowedTools est critique en unattended : il limite exactement ce que Claude peut faire.

Routines : des Claude qui tournent sans vous

Les routines tournent sur l'infrastructure Anthropic. Elles continuent même quand votre machine est éteinte. Créez-les depuis le web, l'app Desktop, ou en session : 

/schedule

Usages typiques :

  • Revue matinale des PR ouvertes.
  • Analyse nocturne des échecs CI.
  • Audit hebdomadaire des dépendances.
  • Sync de la doc après fusion de PR.

Les routines peuvent aussi être déclenchées par événement : un webhook GitHub, un appel API, un message dans un channel.

Tâches programmées Desktop

Les desktop scheduled tasks tournent sur votre machine, avec accès direct à vos fichiers et outils locaux. Mieux adaptées quand la tâche a besoin de votre environnement précis.

/loop — poll dans une session

Pour une surveillance courte à l'intérieur d'une session (vérifier un déploiement, attendre une build) : 

/loop 5m /vérifier-déploiement
/loop 30s /check-tests

GitHub Actions

Un workflow GitHub Actions dédié permet à Claude d'intervenir sur vos PR et issues : triage automatique, revue de code, autofix de CI. L'action officielle se configure en quelques lignes : 

# .github/workflows/claude.yml
name: Claude Code
on:
  pull_request:
  issues:
    types: [opened]
jobs:
  claude:
    runs-on: ubuntu-latest
    steps:
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

GitLab CI/CD

Un support natif existe aussi pour GitLab. Même logique : Claude est déclenché sur événement (MR, issue, pipeline), et il peut commenter, pousser, créer des revues.

Agent SDK : construire vos propres agents

Pour des workflows totalement sur mesure, l'Agent SDK expose les tools et capacités de Claude Code dans votre propre code. Vous contrôlez l'orchestration, les permissions, les outils autorisés, la boucle d'exécution.

Cas d'usage typiques :

  • Un bot interne qui triage les tickets selon vos règles métier.
  • Un pipeline de migration data piloté par un agent.
  • Un assistant intégré à votre produit, utilisant Claude Code pour l'exécution de tâches de code.
À retenir

Les quatre canaux d'automatisation ne s'excluent pas : vous pouvez mettre en place une routine qui déclenche un pipeline CI qui invoque un agent personnalisé qui à son tour spawn des subagents. Commencez simple, montez en abstraction au besoin.

Chapitre 12

Bonnes pratiques

Les patterns qui marchent et les pièges à éviter, condensés par les équipes qui utilisent Claude Code au quotidien.

Donnez à Claude un moyen de se vérifier

C'est la pratique à plus fort levier. Un Claude qui peut lancer ses tests, comparer son résultat à une capture, exécuter un lint, est un Claude qui se corrige tout seul. Sans quoi vous devenez l'unique boucle de rétroaction, et chaque erreur réclame votre attention.

AvantAprès
« implémente une fonction qui valide un email »« écris validateEmail. Cas de test : user@example.com → true, invalide → false, user@.com → false. Lance les tests après »
« rend le dashboard plus joli »« [capture collée] implémente ce design. Prends une capture du résultat, compare, liste les écarts et corrige »
« la build échoue »« la build échoue avec cette erreur : [coller]. Corrige, vérifie que la build passe, traite la cause racine »

Explorer, planifier, implémenter

Laisser Claude coder directement produit souvent du code qui résout un problème légèrement à côté du vôtre. Trois phases séparées donnent toujours de meilleurs résultats :

  1. Exploration en mode plan : « lis /src/auth et explique le flow de session ».
  2. Plan détaillé : « liste les fichiers à modifier, décris le nouveau flow ».
  3. Implémentation en sortant du plan mode : « implémente le plan ».

Prompts précis

VaguePrécis
« ajoute des tests pour foo.py »« écris un test pour foo.py couvrant le cas où l'utilisateur est déconnecté. Évite les mocks »
« pourquoi cette API est si bizarre ? »« parcours l'historique git de ExecutionFactory et résume l'évolution de l'API »
« ajoute un widget calendrier »« regarde HotDogWidget.php, suis le même pattern pour un CalendarWidget avec sélection de mois et pagination d'année »
« corrige le bug de login »« les utilisateurs disent que le login échoue après timeout de session. Vérifie src/auth/, écris d'abord un test qui reproduit, puis corrige »

Gérer son contexte

  • /clear entre tâches sans rapport. Un contexte propre bat toujours un long contexte pollué.
  • Esc pour arrêter Claude dès qu'il part dans la mauvaise direction.
  • /rewind pour annuler proprement et repartir d'un checkpoint.
  • Subagents pour toute recherche qui va lire beaucoup de fichiers.
  • /btw pour les questions de côté qui ne doivent pas rentrer dans le contexte.

Laisser Claude vous interviewer

Pour une fonctionnalité un peu complexe, retournez le processus. Commencez par un prompt minimal : 

Je veux construire [description brève]. Interview-moi en détail avec
l'outil AskUserQuestion.

Pose des questions sur l'implémentation technique, l'UX, les edge cases,
mes préoccupations et les tradeoffs. Pas de questions évidentes, creuse les
points difficiles que je n'ai peut-être pas anticipés.

Continue jusqu'à ce qu'on ait tout couvert, puis écris une spec complète
dans SPEC.md.

Vous obtenez une spec que vous pouvez exécuter dans une session fraîche, avec un contexte propre tout entier dédié à l'implémentation.

Patterns d'échec à repérer

PatternCorrectif
Session fourre-tout — plusieurs tâches sans rapport dans la même conversation/clear entre les tâches
Corrections en boucle — vous corrigez trois fois sur le même pointAprès deux corrections, /clear et prompt plus précis
CLAUDE.md surchargé — Claude ignore les règles noyéesTailler sans pitié, convertir en hook ce qui doit être garanti
Vérification absente — code plausible mais fauxToujours fournir tests, scripts, captures
Exploration infinie — Claude lit 100 fichiersScoper étroitement, ou déléguer à un subagent

Développer son intuition

Les patterns de ce livre sont des points de départ, pas des règles. Parfois vous devez laisser le contexte s'accumuler parce que vous êtes profondément dans un problème complexe. Parfois vous devez sauter la phase plan parce que la tâche est exploratoire. Parfois un prompt vague est exactement ce qu'il faut parce que vous voulez voir comment Claude interprète le problème.

Observez ce qui marche. Quand Claude produit du bon travail, notez ce que vous avez fait : structure du prompt, contexte fourni, mode actif. Quand il peine, demandez-vous pourquoi. Avec le temps, une intuition se construit qu'aucun guide ne peut remplacer.

Le mot de la fin

Claude Code est un collaborateur, pas un oracle. Il devient exceptionnel quand vous lui donnez la structure dans laquelle exceller — un bon CLAUDE.md, des skills bien taillés, des hooks qui garantissent les non-négociables, et un cadre de permissions qui vous laisse dormir tranquille.

Glossaire

Agent SDK
Bibliothèque permettant de construire ses propres agents sur l'infrastructure de Claude Code.
Agentic loop
Boucle fondamentale : prompt → décision d'outils → observation → nouvelle décision, jusqu'à achèvement.
Auto memory
Mémoire automatique que Claude maintient tout seul sous ~/.claude/projects/<projet>/memory/.
Background agent
Session complète qui tourne en parallèle de la vôtre, pilotée depuis une vue de supervision.
Channel
Serveur MCP capable de pousser des événements externes (Telegram, Discord, webhook) dans une session.
Checkpoint
Instantané automatique créé avant chaque modification de fichier, utilisé par /rewind.
CLAUDE.md
Fichier d'instructions persistantes chargé au début de chaque session.
Compaction
Processus de résumé automatique de l'historique quand le contexte approche sa limite.
Dispatch
Service qui spawn des sessions Desktop sur demande depuis votre téléphone.
Hook
Script shell, HTTP, prompt ou agent exécuté à un point précis du cycle de vie.
MCP
Model Context Protocol, standard ouvert pour brancher des outils externes à Claude.
Plan mode
Mode de permission où Claude peut lire mais pas modifier, pour l'exploration et la planification.
Plugin
Package distributable qui combine skills, hooks, subagents et serveurs MCP.
Remote Control
Fonction qui permet de piloter une session locale depuis un téléphone ou un autre navigateur.
Routine
Tâche programmée tournant sur l'infrastructure Anthropic, indépendante de votre machine.
Rule path-scopée
Fichier d'instructions dans .claude/rules/ chargé uniquement pour les fichiers matchant un glob.
Sandbox
Isolation OS qui restreint l'accès au système de fichiers et au réseau pour la session.
Skill
Compétence réutilisable sous forme de dossier contenant un SKILL.md, chargée à la demande.
Subagent
Assistant spécialisé invoqué dans sa propre fenêtre de contexte, avec outils et instructions dédiés.
Teleport
Mécanisme pour transférer une session cloud dans votre terminal local.
Tool Search
Mécanisme qui diffère le chargement des schémas d'outils MCP pour économiser du contexte.
Worktree
Checkout git isolé permettant plusieurs sessions parallèles sur le même dépôt.
